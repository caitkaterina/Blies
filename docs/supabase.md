# Supabase backend implementation and activation

Implemented on branch `feat/supabase-persistence`. The React/Vite frontend remains in its separate repository and has not been changed by this backend work. No remote database migration or deployment has been performed.

## Architecture and schema

`lib/persistence.ts` provides asynchronous enquiry, document metadata, CMS/history, audit and rate-limit operations. `BLIES_STORAGE_MODE=sqlite` retains the existing synchronous SQLite implementation behind those operations. `supabase` uses server-only PostgREST RPCs and Storage HTTPS requests. There is no filesystem fallback in managed mode. Missing credentials, network errors and failed database operations fail closed. Marketing pages retain repository-content fallback when CMS is unavailable.

`supabase/migrations/202610130001_backend.sql` creates the shared `enquiries` table and security-invoker views `contact_enquiries`, `quotation_requests` and `tracking_enquiries`. JSONB preserves all validated quotation/tracking fields and the existing administrator record format. Records have status/queue/email-state constraints and indexes. `documents` has request foreign keys, unique safe object identifiers and restricted media types. `content`, `versions`, `audit_records` and `limits` preserve the existing CMS, change history, audit and rate limiting. Enquiry creation with metadata/audit and administrative updates with audit run in database transactions through restricted RPC functions.

All business tables enable RLS. `anon` and `authenticated` have no table/view or RPC access. Public visitors submit through the backend, not directly through Supabase. The backend service role bypasses RLS, so every administrator route continues to enforce server permissions before accessing the adapter. Audit update/delete privileges are removed from the runtime service role. SQL function execution is revoked from PUBLIC and browser roles. Custom password/TOTP staff accounts, HMAC HttpOnly cookies, admin/editor/sales roles, session expiry and CSRF checks are preserved; durable RPC rate limits also enforce TOTP replay protection. No migration to Supabase Auth or browser-editable administrator table is included. Staff identities/password hashes/TOTP secrets remain in protected backend environment settings.

## Review and configure a staging project

1. Inspect existing project tables, grants/default privileges, RLS/storage policies, Auth settings and buckets. This migration intentionally fails on conflicting existing objects. Back up any existing data and review conflicts; do not replace/drop tables to make it pass. The local PostgreSQL test supplies stub Storage metadata, so it does not verify Supabase's live Storage policies.
2. Review the SQL and apply it only to the selected staging Supabase project using the Supabase migration workflow or SQL editor. These instructions do not authorize changes to production data. Existing SQLite data/CMS is not migrated automatically; a separately reviewed export/import and verification are required if records exist.
3. In backend Vercel environment settings, set `BLIES_STORAGE_MODE=supabase`, `BLIES_SUPABASE_URL` to the exact `https://<project-ref>.supabase.co` origin without trailing slash, and `BLIES_SUPABASE_SERVICE_ROLE_KEY` securely. Never put this key in browser variables or Git. Use Node 24.x, repository root, `npm ci`, `npm run build`, default Next.js output. Do not use static export. Override the older marketing-only `disabled` setting only after staging validation.
4. Set `BLIES_SITE_URL` to the actual backend origin. Set `BLIES_PUBLIC_ORIGINS` to exact approved frontend origins, comma-separated. Preserve the existing protected staff/session settings; configure the approved scanner via `BLIES_SCAN_URL`/`BLIES_SCAN_KEY` and optional Resend sender/key via `BLIES_EMAIL_FROM`/`BLIES_EMAIL_API_KEY`. Keep launch approval false until the existing reviews are complete. Configure network access for the project's Supabase hostname, approved scanner and api.resend.com where used. Values belong in deployment secret settings.
5. Verify PostgreSQL writes, role rejection, actual private Storage behavior, staff MFA/replay protection, signed URL expiry, scanner failure and both deployed origins in staging before production rollout.

## Public API contract

- `POST /api/contact`: JSON `{locale, name, email, company?, message, consent:true, website:""}`.
- `POST /api/tracking`: existing JSON tracking fields (`locale`, `shipment`, `company`, `name`, `email`, `phone`, optional `notes`, `consent:true`, honeypot `website:""`).
- `POST /api/quotes`: existing multipart contract: `data` is a JSON string conforming to `lib/validation.ts`; optional repeated `files` fields. All route/cargo/specification fields are preserved. Managed mode caps total request bytes at 3 MiB, each file at 2 MiB, total files at 2 MiB and count at three. SQLite retains the existing 10 MiB/file limit and 31 MiB total request limit.

Success is HTTP 201 with `{reference, received:true, emailStatus}` only after the transaction commits. Email delivery may be `pending` or `not-configured`; it is not proof of email delivery. If persisting the email outcome fails after receipt, the request remains accepted and the database stays pending rather than falsely reporting submission failure. Operators must reconcile pending email states. Validation errors return 422, origin/permission denial 403, rate limiting 429, storage/scanner unavailability 503 and oversized bodies 413. Streamed body limits do not trust Content-Length. Frontend retries after ambiguous transport failures can still duplicate requests; durable submission idempotency/outbox delivery is a future enhancement.

`OPTIONS` and POST responses allow only approved exact origins, POST and Content-Type. CORS never enables cookies/credentials. Public endpoints retain global/email limits and honeypot validation; CORS is not bot protection. Production needs trusted edge abuse controls; do not trust arbitrary client IP headers. Administrator routes remain on the backend origin and require the existing cookies/roles and CSRF token. Do not expand their origin checks to the public allowlist. Use `/admin` on the backend itself rather than embedding it cross-site.

To connect the separate React frontend later, submit the contracts above with `credentials: 'omit'` to the configured backend API origin and show success only after checking status 201 and `received === true`. Add the actual backend origin to the frontend's CSP connect-src if CSP is configured there. Contact currently lacks consent UI, so explicit consent must be added when wiring it. Existing frontend forms remain email-only until that separate integration is completed.

## Private documents

`blies-private` is a private bucket with a 2 MiB object limit and PDF/JPEG/PNG restrictions. The backend signature-checks and scans bytes with the existing required HTTPS scanner before uploading under a generated UUID; user filenames are never paths. No public Storage policy is added. Objects that fail metadata commit are removed on a best-effort basis; failed cleanup can leave inaccessible orphan objects requiring operator reconciliation. Database and object storage cannot share a transaction. Do not relax scanner checks to enable uploads.

Downloads through `/api/admin/documents/[id]` require an admin/sales session, append an audit event, then redirect to a 60-second signed attachment URL in managed mode. Responses use no-store/referrer protection. A signed URL is a temporary bearer credential: do not log or share it. SQLite still streams local files. Existing browser-to-Vercel multipart uploads use deliberately smaller limits; 10 MiB uploads require a separate reviewed direct-to-quarantine upload/scanning design and are not implemented here.

## Validation and limits

Run `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`, `npm run test:e2e`, `npm run test:vercel` and `npm run test:storage-failure`. PostgreSQL tests use PGlite with test-only roles and Storage metadata; HTTP adapter tests use mocked fetch and dummy credentials. Browser tests use isolated temporary SQLite records and a scanner-contract fixture, not a malware engine. Neither establishes live Supabase Storage/PostgREST connectivity or production security. See the final implementation report for actually executed results.
